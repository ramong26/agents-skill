# 개발 기획서 문서 디자인

초안 작성과 최종 조판에 공통 적용한다. 기존 목차·장 순서·업무 흐름·기능·완료 조건은 유지하고 표현과 배치만 정리한다. 참고 문서는 폰트·위계·목록·표·간격의 참고로 사용한다. 사용자 지정 서식·색상을 우선하고 기존 인쇄 규격과 최소 글자 크기를 유지한다.

## 페이지 구성

- 표지: 큰 제목 `프로젝트명 개발기획서`와 `담당자: 김수연 | 날짜: YYYY년 M월 D일` 두 요소만 배치한다. 담당자는 사용자가 변경하면 그 값을 사용하고 날짜는 지정일, 없으면 작성일을 쓴다. 부제·버전·설명 문단·도식은 넣지 않는다.
- 두 번째 페이지: 기존 목차 항목·순서·점선·쪽번호 형식을 유지하고 최종 PDF의 실제 쪽수와 맞춘다.
- 장 시작: 장 번호·제목·핵심 요약을 일관된 형식으로 둔다. 장마다 별도 페이지를 강제하지 않는다.
- 본문: 아래 기준으로 표·리스트·도식을 선택한다. 실제 날짜가 미정이면 일정은 단계·의존 관계로 표시한다.
- 내용이 적은 페이지: 기존 순서대로 다음 관련 블록을 같은 쪽에 배치할 수 있는지 검토한다. 표지·목차·독립 도식의 의도적인 여백은 유지한다. 목표 쪽수나 점유율을 강제하지 않는다.

## 인쇄 규격과 서체

- A4 세로. 여백 위 25mm·아래 22mm·좌우 24mm, 머리말·꼬리말은 종이 끝에서 10mm.
- Pretendard Regular 본문 11pt, Bold 장 제목 18pt·소제목 14pt. 표·캡션·쪽번호·도식과 화면 라벨은 최종 인쇄 크기에서 최소 10.5pt. 참고 문서의 작은 글씨와 좁은 여백은 복제하지 않는다.
- 본문 줄간격 1.4배, 문단 뒤 3mm, 장 제목 뒤 6mm, 소제목 앞 9mm·뒤 4mm, 표·목록과 다음 소제목 사이 최소 9mm. 셀 여백 위아래 2.5mm·좌우 3mm.
- DOCX 기본 스타일과 개별 run의 영문·동아시아 서체를 함께 지정한다. 표·머리말·캡션도 확인하고, 그림에 쓰인 폰트는 별도로 확인한다. 생성 API의 font 이름 지정만으로 한글 적용을 보장했다고 판단하지 않는다.
- PDF에서 실제 폰트 리소스·크기와 렌더 결과를 확인한다. 설정과 다른 서체가 기록되면 원본 스타일·변환 과정을 조사한다. 지정 서체 누락·대체나 DOCX 렌더 불가는 검증 제한으로 보고하고 지정 서체·동일 출력이 검증됐다고 주장하지 않는다. PDF의 폰트 이름만으로 한글 대체 서체를 단정하지 않는다.

## 독자가 읽는 표현

- 근거·출처 열, 원문 제목·절·쪽번호, 내부 대조 기록과 도구명·렌더링·검증 같은 제작 과정 문구는 납품 본문에서 제외한다. 검토용 기록은 내부 전달에만 사용한다. 제품이 실제 사용하는 기술·외부 API는 기술스택에 유지한다.
- 소스 파일 경로·파일별 코드 위치·구현 조사 기록은 제외하고 사용자 기능·처리·결과로 설명한다. 필수 데이터 규격과 API 계약은 해당 설계 장에서 유지한다.
- 확정 내용은 자연스러운 문장으로 쓴다. 제안·미정 내용은 필요한 곳에만 `설계제안: 짧은 설명`, `확인사항: 결정할 내용`으로 쓴다. `[원문의 목표]`, `[확인된 사실]`, `[설계 제안]` 같은 대괄호 라벨은 쓰지 않는다.
- 화면 그림의 버튼은 버튼 모양으로, 입력은 테두리 있는 입력란으로 표현한다. `[저장]`, `이름 [ ]` 같은 텍스트 대용 표기는 쓰지 않는다. 기술 문법에 필요한 대괄호는 임의 삭제하지 않는다.

## 내용에 맞는 배치

| 내용 | 표현 | 구성 |
|---|---|---|
| 개발 범위·향후 기능 | 기능별 소제목과 리스트 | 기능명 아래 주요 동작·결과·제외 조건을 짧게 나열 |
| 요구사항 비교·권한·데이터 항목 | 표 | 같은 속성을 열로 두고 한 행에 한 항목 |
| 기능 상세·핵심 로직·비기능 조건 | 소제목과 리스트 | 처리·오류·완료 조건을 구분; 비교가 필요한 부분만 표 |
| 기술스택 | 분야별 표 | 분야 / 기술 / 용도; 프론트엔드·백엔드·데이터 저장·인프라·외부 API로 구분 |
| 절차·아키텍처·일정 | 도식·타임라인 또는 일정표 | 기존 순서·분기·의존 관계 유지 |
| 화면안 | 정적 와이어프레임과 짧은 설명 | 실제 위치 관계는 그림으로, 설명은 그림 밖에 배치 |

기술스택에서 미정 분야는 `미정`, 제안 기술은 기술명 옆에 `설계제안`을 적는다. 표를 채우기 위해 새 기술을 추가하지 않는다.

## 정보 단위와 표 구조

- 설명은 `기능 소제목 → 한 문장 요약 → 필요한 라벨별 리스트`로 작성한다. 역할·입력·처리·결과·오류·완료 조건을 긴 문단 하나에 합치지 않는다. 항목은 한 동작·조건씩 보통 1~2줄로 쓰고 길어지면 의미 단위로 나눈다. 기존 내용과 ID 연결은 유지한다.
- 기능 상세는 `역할·진입 조건 / 입력·검증 / 처리·상태 / 결과·오류·복구 / 완료 기준`을 짧은 굵은 라벨과 목록으로 구분한다. 기존 순서와 동작은 유지하며 화면 설명만으로 대체하지 않는다. 분기·검사 단계는 번호 목록, 비교 가능한 값은 표로 둔다.
- 요구사항 표의 상태는 `확정 / 설계제안 / 미정`처럼 짧게 적는다. 확정 요구의 세부 미정은 표 아래 `확인사항: 요구 ID — 결정할 내용` 목록으로 연결한다. 요구 전체를 미정으로 바꾸거나 상태 셀에 긴 확인 내용을 합치지 않는다. 확인 내용 자체를 비교해야 할 때는 별도 열을 둔다.
- ID·상태 같은 짧은 열은 좁게, 설명 열은 넓게 배분한다. 3줄 이상 셀이 반복되면 열폭·분류·표 밖 상세를 검토한다. API·버전·식별자의 의미를 자르지 않는다. 긴 기술명은 버전·용도와 구분해 배치한다.
- 같은 기능의 처리·오류·완료 조건을 표 밖으로 옮길 때 요구 ID로 연결한다. 셀 안에 여러 동작이 있으면 불릿으로 구분한다. 긴 표는 페이지를 나누고 머리글을 반복한다. 글자를 줄여 표를 맞추지 않는다.

예: 상태 셀의 `확정; 저장 형식 미정`은 상태 `확정`과 표 아래 `확인사항: FR-01 — 저장 형식 결정`으로 분리한다. 기능 자체와 남은 결정의 범위는 그대로 유지한다.

## 글꼴·색상·표

- 본문은 검정 `#151A20`, 장 제목·기능 소제목은 네이비 `#1A304B`와 굵기로 구분한다. 기본 강조색은 파랑 `#245A81`, 보조 설명은 회색 `#66727E`로 둔다.
- 핵심 완료 조건·중요 제한·확인사항은 짧은 구절에 굵기와 강조색을 적용한다. 긴 문단 전체를 칠하지 않는다. 필요하면 연한 배경 `#EEF3F8`의 안내 영역으로 묶는다. 상태 의미는 텍스트로 함께 적는다.
- 표 머리는 연회색 `#EEEEEE`와 검정 글자를 기본으로, 그룹 칸은 필요할 때 `#F6F6F6`으로 구분한다. 본문은 흰색 중심, 구분선은 `#BDBDBD` 0.5~0.75pt로 두고 제목·표·설명의 좌측 축을 맞춘다. 사용자 지정 표 색상이 있으면 우선한다.
- 리스트는 한 항목에 한 동작·조건을 적고 들여쓰기와 항목 간격을 통일한다. 소제목과 다음 내용의 간격을 일정하게 유지한다.

흑백에서도 굵기·라벨·경계로 중요도와 상태를 구분할 수 있어야 한다. 회색 보조 설명도 최소 글자 크기를 유지한다.

## 페이지 경계와 화면안

- 제목은 첫 설명·표 머리와 함께 둔다. 짧은 기능 블록·목록 항목·표 행은 의미 없이 갈라지지 않도록 한다. 긴 문단은 목록으로 구조화하거나 자연스럽게 나눈다. 전체 장·긴 표에 한꺼번에 keep-with-next를 적용해 큰 공백을 만들지 않는다.
- 앞 장의 짧은 문장 꼬리가 다음 장 제목 위에 남으면 해당 설명 단위를 재배치한다. 이어지는 표는 반복 머리글을 유지하고 필요한 경우 계속 표기를 붙인다.
- 화면마다 한 페이지를 강제하지 않는다. 인접한 간단 화면은 라벨 최소 크기와 화면→설명→다음 화면 순서가 유지될 때 같은 쪽 위아래로 묶을 수 있다. 복잡한 화면은 독립 페이지를 유지한다. 가로 두 화면 배치나 목표 쪽수를 위해 축소하지 않는다.
- 화면별 고유 입력·동작·상태·오류·인계는 남기고, 동일한 공통 규칙은 한 번 정리한다. 확인 목록도 항목과 설명이 떨어지지 않게 배치한다. 여백을 채우기 위한 장식·새 기능·반복 설명은 추가하지 않는다.

## 렌더링 검토

전체 조판 전에 표지와 가장 긴 기능·상태표·화면안·페이지 경계를 포함하는 대표 샘플을 렌더한다. 작은 요청은 실제 산출물 자체로 확인한다. 원래 크기로 서체·크기·표 줄바꿈·정보 위계를 확인한 뒤 전체에 적용한다.

전체 렌더에서는 축소본으로 밀도 편차와 반복 공백을 찾고, 원래 크기로 글꼴·대비·라벨·제목 고립·문장 꼬리·표 분할을 확인한다. 추출 텍스트만으로 점선·띄어쓰기·겹침을 판단하지 않는다. 변경 전후 목차·업무 흐름·기능·입력·오류·완료 조건을 대조하고 수정 후 다시 렌더한다.
