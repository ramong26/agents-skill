# 개발 기획서 문서 디자인

팀장 검토에서 조판 전에 읽는다. 사용자 지정 서식·색상을 우선하고, 기존 인쇄 규격과 최소 글자 크기를 유지한다. 디자인은 사실을 추가하는 대신 정보의 중요도와 관계를 드러낸다.

## 페이지 구성

- 표지: 프로젝트명, 한 문장 목적, 문서 버전·날짜를 서로 다른 위계로 배치한다. 프로젝트의 핵심 흐름을 표현하는 도식을 사용할 수 있다.
- 장 시작: 장 번호·제목·핵심 요약을 일관된 형식으로 둔다. 장마다 별도 페이지를 강제하지 않는다.
- 본문: 비교는 표, 절차는 흐름도, 권한은 매트릭스, 일정은 타임라인, 기능 상세는 항목별 명세로 표현한다. 실제 날짜가 미정이면 일정은 단계·의존 관계로 표시한다.
- 원문 사실·설계 제안·미결정 사항: 텍스트 라벨과 일관된 서식으로 구분한다. 색에만 의존하지 않는다.
- 내용이 적은 페이지: 관련 내용을 합치거나 흐름을 재배치한다. 의도적인 여백은 유지하고 빈 공간을 채우기 위한 장식·반복 설명은 추가하지 않는다.

## 긴 명세와 표

표에는 비교할 수 있는 짧은 정보를 두고, 긴 처리·오류·완료 기준은 표 밖에서 요구 ID로 연결한다. 열 너비는 내용 길이에 맞추고 반복 머리글을 적용한다. 셀 테두리와 채움색은 정보 구분에 필요한 만큼만 사용한다. 글자를 줄여 표를 맞추지 않는다.

예: `ID / 요구사항·상태 / 입력과 결과 / 검수 조건 / 근거`의 각 셀이 긴 문단이면 비교 표를 `ID / 요구사항·상태 / 입력과 결과`로 줄이고, 표 아래에서 같은 ID별로 `처리 / 오류 / 완료 기준 / 근거`를 설명한다. 원문 근거와 검수 조건은 모두 유지한다.

## 렌더링 검토

표지·본문·상세 명세 샘플에서 제목과 보조 정보의 구분, 읽는 순서, 표 줄바꿈, 그림 라벨 크기를 확인한다. 전체 조판 후에는 페이지 축소본으로 반복 구성과 의도하지 않은 빈 공간을 찾고, 원래 크기로 본문·표·도식의 가독성을 확인한다. 시각화와 명세가 같은 요구 ID·상태·권한을 설명하는지 대조한다.
