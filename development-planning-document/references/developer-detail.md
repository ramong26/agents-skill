# 개발자 상세 기준

03~07장은 기능 소개가 아니라 구현 경계와 검수 가능한 동작을 보여준다. 자료에 없는 구조·기술은 **제안**으로 표시한다. 미정 수치에는 임의 값을 넣지 않고 설정값, 측정 방법, 결정 책임을 적는다.

## 03 개발 범위

- 요구사항 ID별 포함 모듈, 사용자, 산출물, 외부 의존, 제외 범위, 완료 증거를 연결한다.
- MVP와 후속 단계를 나누고 인터페이스·데이터 이관·운영 문서도 범위에 포함할지 명시한다.

## 04 핵심 설계

- 역할별 읽기·쓰기·승인 권한을 표로 정의한다.
- 핵심 엔터티의 키, 연결, 주요 필드, 고유 제약, 보유·삭제 책임을 정의한다.
- 업무 상태와 허용 전이, 사람 승인, 비동기 작업, 실패 복구를 적는다.
- 외부 시스템과 내부 시스템의 경계, 저장 위치, 호출 책임을 구분한다.

## 05 기능 상세

각 기능을 `역할·진입 조건 → 입력과 검증 → 처리·상태 변화 → 출력·오류 → 완료 기준` 순서로 쓴다. 화면만 설명하지 않는다. 비동기 기능에는 작업 조회와 재시도, 승인 기능에는 승인·반려와 이력을 포함한다. API 경로·필드는 합의 전이면 계약 초안으로 표시한다.

## 06 핵심 로직

- 계산식은 분자·분모, 측정 시점, 0건·중복·취소·수정 처리를 함께 적는다.
- 생성 작업은 입력 검사, 요청 식별자, 비용 상한, 중복 방지, 시간 초과, 재시도·수동 대체, 로그를 적는다.
- 규격 검사는 설정값 출처, 검사 순서, 실패 코드, 승인자, 재검사 기준을 적는다.
- 판단이 갈릴 분기에는 의사코드 또는 입력·기대 결과 예시를 넣는다.

## 07 기술스택

확정된 외부 연동과 제안 프레임워크를 분리한다. 계층마다 선택 이유, 대안, 운영 비용·보안·인수인계 영향을 적는다. DB·파일 저장·작업 큐·보고서 생성·배포·모니터링을 빠뜨리지 않는다. 원문에 없는 제품명은 권장안으로만 제시한다.
