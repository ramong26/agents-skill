# 개발 기획서 팀장 검토

세 전문 초안이 모두 도착한 다음 실행한다. 각 초안의 결론을 그대로 이어 붙이지 말고 원문, 요구 ID, 역할과 상태 흐름을 대조한다.

## 통합 검토

1. 원문 사실, 원문의 목표, 구현 제안, 계약 전 결정사항을 내부 검토에서 구분한다. 납품 본문에는 목표를 문장으로 설명하고 필요한 곳만 `설계제안:`, `확인사항:`으로 표시한다. 참고 문서의 프로젝트 사실은 가져오지 않는다.
2. 모든 REQ ID를 개발 범위, 기능 처리·오류·완료 기준, 검수 증거와 연결한다. 누락·중복·범위 밖 항목을 고친다.
3. 화면의 필드와 동작이 데이터 모델·권한·상태 전이·보고 계산에 실제로 연결되는지 확인한다. 자료에 나온 역할 간 인계 지점을 맞춘다.
4. 같은 수치의 분모·단위·측정 시점을 확인한다. PoC·검수·파일럿의 표본과 목표, 가능 판정과 실제 성공률을 구분한다.
5. 수치·기간·정책이 원문에서 제안인 경우 실적·확정 규격처럼 쓰지 않는다. 불일치는 수정하거나 `계약 전 확인`에 모은다.

## 산출물별 필수 스킬

조건에 해당하면 이름만 나열하지 말고 해당 스킬을 읽고 적용한다.

| 산출물 | 필수 스킬 |
|---|---|
| 편집 가능한 DOCX | `documents:documents` |
| PDF 생성·변환·최종 시각 검토 | `pdf:pdf` |
| 편집 가능한 FigJam 다이어그램 | `figma:figma-generate-diagram` |
| React 제품 화면의 실제 구현 | `product-ui` |

아키텍처와 파이프라인은 개발 에이전트가 `archify`로 생성·검증한 도식을 사용한다. FigJam이 요구되면 편집본을 별도 산출물로 만든다. 화면 구성안만 요구되면 실제 React 구현으로 확대하지 않는다.

## 조판과 출력 검증

[문서 디자인 기준](../references/document-design.md)을 읽고 인쇄 수치·서체·색상·정보 구조를 적용한다. 긴 기능 초안은 라벨별 목록으로, 상태와 세부 미정은 짧은 상태표와 ID별 확인사항으로 나눈다. 데이터·권한·입력·오류·완료 기준은 유지한다.

전체 조판 전에 표지와 가장 긴 기능·상태표·화면안·페이지 경계가 포함된 대표 샘플을 렌더링해 수정한다. 작은 요청은 실제 산출물 자체로 확인한다. 샘플 확인은 내부 검토로 수행한다.

## 제출 전 검사

1. DOCX의 기본 스타일·개별 run·동아시아 서체와 그림 폰트를 확인하고 PDF의 실제 폰트 리소스·크기를 대조한다. 다른 서체가 기록되면 원본 설정·변환 과정을 조사한다. 서체명만으로 한글 대체 서체를 단정하지 않는다.
2. DOCX와 PDF의 모든 페이지를 실제 렌더링해 한글·라벨 크기·겹침·잘림·이미지 선명도·목차 쪽수를 확인한다. 추출 텍스트의 점선·공백 이상은 시각 렌더와 구분한다.
3. 긴 셀·반복 상태 설명·목록화 누락·핵심 강조·흑백 식별성을 확인한다. 제목 고립, 앞 장 문장 꼬리, 표 행·확인 목록의 부자연스러운 분할과 반복되는 큰 공백을 수정한다. 복잡한 화면은 글씨를 줄여 합치지 않는다.
4. 근거·코드 위치·대괄호 상태 라벨과 내부 도구·렌더·검증 과정 문구를 납품 본문에서 정리한다. 제품 기술과 필수 API 계약은 유지한다.
5. 변경 전후 요구 ID·장 순서·업무 흐름·기능·입력·오류·완료 기준을 대조하고 수정 후 다시 렌더한다. 최종 보고에는 결정 필요 항목과 실제 검증 결과·미확인 사항을 구분한다. 구조 validator 통과를 시각 품질 통과로 보고하지 않는다.
