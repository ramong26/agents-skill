# 개발 기획서 팀장 검토

세 전문 초안이 모두 도착한 다음 실행한다. 각 초안의 결론을 그대로 이어 붙이지 말고 원문, 요구 ID, 역할과 상태 흐름을 대조한다.

## 통합 검토

1. 원문 사실, 원문의 목표, 구현 제안, 계약 전 결정사항을 내부 검토에서 구분한다. 납품 본문에는 목표를 문장으로 설명하고 필요한 곳만 `설계제안:`, `확인사항:`으로 표시한다. 참고 문서의 프로젝트 사실은 가져오지 않는다.
2. 모든 REQ ID를 개발 범위, 기능 처리·오류·완료 기준, 검수 증거와 연결한다. 누락·중복·범위 밖 항목을 고친다.
3. 화면의 필드와 동작이 데이터 모델·권한·상태 전이·보고 계산에 실제로 연결되는지 확인한다. 자료에 나온 역할 간 인계 지점을 맞춘다.
4. 같은 수치의 분모·단위·측정 시점을 확인한다. PoC·검수·파일럿의 표본과 목표, 가능 판정과 실제 성공률을 구분한다.
5. 수치·기간·정책이 원문에서 제안인 경우 실적·확정 규격처럼 쓰지 않는다. 불일치는 수정하거나 `계약 전 확인`에 모은다.

## 산출물별 필수 스킬

조건에 해당하면 이름만 나열하지 말고 해당 스킬을 읽고 적용한다.

| 산출물 | 필수 스킬 |
|---|---|
| 편집 가능한 DOCX | `documents:documents` |
| PDF 생성·변환·최종 시각 검토 | `pdf:pdf` |
| 편집 가능한 FigJam 다이어그램 | `figma:figma-generate-diagram` |
| React 제품 화면의 실제 구현 | `product-ui` |

아키텍처와 파이프라인은 개발 에이전트가 `archify`로 생성·검증한 도식을 사용한다. FigJam이 요구되면 편집본을 별도 산출물로 만든다. 화면 구성안만 요구되면 실제 React 구현으로 확대하지 않는다.

## 문서 구성과 인쇄 규격

전체 조판 전에 [문서 디자인 기준](../references/document-design.md)을 읽고 표지·본문·상세 명세 각 1쪽을 샘플로 렌더링한다. 샘플에서 정보 위계, 내용에 맞는 표현, 표의 줄바꿈과 정보 밀도를 확인·수정한 뒤 같은 기준으로 전체 문서를 구성한다. 1페이지 요청은 해당 페이지 자체로 확인한다. 샘플 확인은 내부 검토로 수행한다.

- A4 세로. 본문 여백: 위 25 mm, 아래 22 mm, 좌우 각 24 mm. 머리말·꼬리말은 종이 끝에서 10 mm.
- Pretendard 사용. 보이는 모든 글자는 최소 14 px 상당인 10.5 pt. 본문 11 pt, 표·캡션·쪽번호 10.5 pt, 장 제목 18 pt, 소제목 14 pt. 표·도식이 넘치면 글자를 줄이지 말고 쪽을 나눈다.
- 본문 줄간격 1.4배, 문단 뒤 3 mm, 장 제목 뒤 6 mm, 소제목 앞 9 mm·뒤 4 mm, 표 또는 목록과 다음 소제목 사이 최소 9 mm, 셀 여백 위아래 2.5 mm·좌우 3 mm.
- 본문·제목·강조·표 색상은 문서 디자인 기준을 적용한다. 사용자 지정 색상을 우선한다.
- 표지와 목차는 각각 독립 페이지다. 목차 페이지 번호는 최종 PDF 쪽수와 대조한다. 본문 장은 내용의 흐름에 따라 자연스럽게 넘긴다.

## 제출 전 검사

DOCX와 PDF를 실제 렌더링해 모든 페이지를 눈으로 확인한다. 빠진 한글 글리프, 14 px 미만의 표·도식 라벨, 표 잘림, 제목과 다음 내용의 분리, 표·목록과 다음 제목의 간격, 목차 쪽수, 이미지 선명도를 수정한다. 문서 디자인 기준에 따라 과도한 표 줄바꿈, 내용과 맞지 않는 반복 구성, 의도하지 않은 빈 공간, 핵심 정보의 식별성도 검사한다. 근거·출처 표시, 코드 위치 설명, 대괄호 상태 라벨이 납품 본문에 남았는지 확인하고 정리한다. 최종 결과에는 결정이 필요한 항목을 간단히 알린다.
