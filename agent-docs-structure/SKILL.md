# Agent Docs Structure

대화 컨텍스트는 사라지지만 파일은 남는다. 에이전트가 매번 같은 경로로 파일을 읽어 현재 위치를 복원하도록 문서 구조를 고정한다.

이 스킬은 다섯 가지 작업을 한다. 사용자의 요청을 아래 중 하나로 분류하고 해당 절만 실행한다.

| 요청                                   | 절                |
| -------------------------------------- | ----------------- |
| 문서 구조를 처음 세운다                | 1. 구조 생성      |
| 새 작업/기능을 시작한다                | 2. 작업 폴더 생성 |
| 체크를 끝냈다 / 작업을 마쳤다          | 3. 상태 동기화    |
| 어디까지 했는지 확인한다 / 이어서 한다 | 4. 현재 위치 복원 |
| 문서가 중복되거나 길어졌다             | 5. 구조 점검      |

## 공통 원칙

- **문서는 주제가 아니라 수명으로 나눈다.** 영구(구조 결정) / 단계(개월) / 작업(시간~일)이 섞이면 짧은 수명 쪽을 고칠 때마다 긴 수명 문서의 신뢰도가 떨어진다. 수명이 다른 축이 또 있으면 그 축도 별도 파일로 분리한다.
- **어느 문서도 가리키지 않는 문서는 만들지 않는다.** 새 문서는 `AGENTS.md`의 읽기 순서 표와 폴더 구조 양쪽에 반드시 등장시킨다. 등장시킬 자리가 없으면 그 문서는 필요하지 않다.
- **문서 하나가 200줄을 넘으면 더 쓰지 않는다.** 책임을 나눌 기준과 예상 줄 수를 제안해 사용자 승인을 받은 뒤 분리한다. 혼자 분리하면 수명이 아니라 길이로 쪼개서 엉뚱한 경계가 생긴다.
- **작업 하나 = 폴더 하나 = 브랜치 하나 = PR 하나.** 이 등식이 깨지면 진행도와 Git 이력이 어긋난다.
- **완료 조건은 검증 가능한 문장으로 쓴다.** "잘 동작한다"는 완료 조건이 아니다. 무엇을 실행하면 어떤 출력이 나오는지 쓴다. 충족하지 못한 항목은 체크하지 않고 남은 내용을 보고한다.
- **문서로 못 막는 것은 설정으로 막으라고 안내한다.** 작성 형식·읽기 순서·분리 기준은 문서로 충분하다. 승인 없는 커밋/푸시, 되돌릴 수 없는 명령은 에이전트 설정의 권한 거부 목록으로 막아야 한다.

## 1. 구조 생성

기존 문서를 먼저 확인한 뒤 아래를 만든다. 템플릿은 `references/templates.md`에 있다.

```text
AGENTS.md               # 진입점. 읽기 순서 / 폴더별 책임 / 변경 규칙 / 작업 종료 전 확인
docs/
├── tasks/
│   └── README.md       # 전체 작업 목록 표와 상태
└── structure/
    ├── ARCHITECTURE.md # 바뀌지 않는 구조 결정
    └── ROADMAP.md      # 단계 구분과 완료 조건
```

- `AGENTS.md`(또는 프로젝트가 쓰는 `CLAUDE.md`)에 네 절을 넣는다: 읽기 순서, 폴더별 책임, 변경 규칙, 작업 종료 전 확인.
- 읽기 순서는 **무조건 실행되는 번호 매긴 단계**로 쓴다. "작업 종류에 따라" 같은 분기 아래에 두면 건너뛴다. 마지막 줄에 "사용자에게 무엇을 할지 묻기 전에 여기까지 확인한다"를 명시한다.
- 프로젝트에 수명이 다른 축(기기별 실측값, 권한 경계 등)이 있으면 `docs/structure/`에 파일을 추가하고 `AGENTS.md`에도 등재한다. 없으면 만들지 않는다.
- **작업 목록 표는 처음부터 전부 만든다.** 스텝 파일은 만들지 않는다.

## 2. 작업 폴더 생성

순서대로 하고 **4번에서 멈춘다.**

1. `docs/tasks/README.md`에서 다음 작업과 범위를 확인한다.
2. `docs/tasks/NN-<작업>/` 폴더와 `README.md`를 만든다. 목표, 스텝 목록, 완료 조건을 쓴다.
3. 스텝마다 `NN-<스텝>.md`를 만들고 체크 항목과 완료 조건을 쓴다.
4. **여기까지를 사용자에게 보여주고 검토를 받는다. 승인 전에는 구현을 시작하지 않는다.**
5. 승인 후 체크 항목 순서대로 진행한다.

체크박스 입도:

- 체크 하나에 1시간이 넘게 걸리면 쪼갠다. 5분이면 끝나는 것은 합친다.
- 체크박스를 3단으로 겹쳐 쓰지 않는다. 스텝이 늘면 깊이 대신 **파일을 늘린다.**
- 조건("로그인한 사용자만 볼 수 있다")은 체크박스가 아니라 `완료 조건` 절에 쓴다.

**지금 시작하는 작업의 스텝만 쓴다.** 앞 작업의 결과에 따라 뒤 작업의 스텝이 달라지므로 미리 쓰지 않는다.

## 3. 상태 동기화

체크 하나를 끝낼 때마다 네 곳을 **같은 값으로** 맞춘다. 한 곳만 고치면 다음에 읽을 때 어디가 맞는지 알 수 없다.

1. 스텝 파일의 `- [ ]` → `- [x]`
2. 작업 폴더 `README.md`의 스텝 목록 진행도와 `이어서 할 일` 줄
   - 형식: `- [ ] 02-스텝이름 — 진행 중 (3/9)`. 체크박스만 있으면 9개 중 3개 한 상태와 0개 한 상태가 똑같아 보인다.
3. `docs/tasks/README.md` 작업 목록 표의 상태
4. `docs/structure/ROADMAP.md` 해당 단계의 상태 줄 — **그 단계의 모든 작업이 끝날 때만** `완료`로 바꾼다

세션용 임시 할 일은 파일로 만들지 않는다. 에이전트 내부 할 일 목록에만 둔다.

작업이 끝나도 폴더를 지우지 않는다. 스텝 파일의 `메모` 절에 실측값과 판단 근거를 남긴다. 이것이 결정 근거를 보존하는 유일한 장치다.

## 4. 현재 위치 복원

파일 세 번만 읽고 다음 행동을 정한다. 사용자에게 되묻기 전에 여기까지 한다.

1. `docs/tasks/README.md` — 표에서 `진행 중`인 작업을 찾는다.
2. 그 작업 폴더의 `README.md` — 진행도와 `이어서 할 일` 줄을 읽는다.
3. 해당 스텝 파일 — 체크되지 않은 첫 항목이 다음에 할 일이다.

네 곳의 상태가 어긋나 있으면 임의로 고르지 말고 어긋난 지점을 보고한 뒤 어느 쪽이 맞는지 확인받는다.

## 5. 구조 점검

다음을 찾아 보고한다. 고치는 것은 보고 후 승인을 받고 한다.

- `AGENTS.md`의 읽기 순서 표와 폴더 구조 어느 쪽에도 없는 문서 (가장 위험하다. 읽히지 않으므로 갱신되지 않고, 폐기된 내용을 담은 채 남는다)
- 200줄을 넘는 문서 → 수명 기준 분리안과 예상 줄 수를 제안한다
- 네 곳의 상태가 어긋난 지점
- 스텝 파일 없이 폴더만 있는 작업, 작업 목록 표에 없는 작업 폴더
- 3단 중첩 체크박스

문서를 지우기 전에 어디서 참조되는지 **전부** 찾는다. 파일 검색은 대소문자를 구분할 수 있으므로 대소문자 무시 검색(`grep -ri`)을 쓴다.
