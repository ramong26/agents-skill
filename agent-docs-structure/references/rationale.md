# 규칙의 근거와 적용 범위

근거 없는 규칙은 지켜지지 않는다. 아래 규칙은 선험적 설계가 아니라 실제로 깨진 것을 고친 결과다.

## 구조가 풀려는 세 가지 손실

| 손실                 | 원인                                                         | 결과                                  |
| -------------------- | ------------------------------------------------------------ | ------------------------------------- |
| 에이전트의 맥락 소실 | 컨텍스트는 길어지면 압축되고 세션이 바뀌면 사라진다          | 어제 정한 결정을 오늘 다시 설명한다   |
| 사람의 기억 소실     | 며칠 간격으로 작업하면 어디까지 했는지 잊는다                | 다음에 할 일을 매번 다시 판단한다     |
| 결정 근거 소실       | 무엇을 했는지는 코드에 남지만 왜 그렇게 했는지는 남지 않는다 | 되돌릴 수 있는 결정을 되돌리지 못한다 |

## 관찰된 실패 → 규칙

| 관찰된 실패                                                                                                                                                                                      | 추가된 규칙                                                                                     |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------- |
| 아무도 가리키지 않는 기획 문서가 폐기된 기술 선택을 설명한 채 300줄 넘게 남아 있었다. 한 번도 읽히지 않아 한 번도 갱신되지 않았고, 에이전트가 읽었다면 확정된 스택과 모순되는 작업을 했을 것이다 | 모든 문서는 `AGENTS.md`의 읽기 순서 표와 폴더 구조 양쪽에 등장해야 한다                         |
| 에이전트가 체크박스를 갱신하지 않았다                                                                                                                                                            | 작업 종료 전 확인 절에 체크 갱신과 4곳 동기화를 항목으로 넣는다                                 |
| 에이전트가 요청받지 않은 변경까지 커밋했다                                                                                                                                                       | 직전 요청의 승인을 그 뒤에 만든 변경으로 확대 적용하지 않는다                                   |
| 작업 폴더를 하나만 만들어 두어 나머지 작업을 잊었다                                                                                                                                              | 작업 목록 표는 처음부터 전부 만들고, 스텝만 시작 시점에 쓴다                                    |
| 진행도가 체크박스로만 표시되어 3/9와 0/9가 구분되지 않았다                                                                                                                                       | 진행도를 `(끝낸 수/전체 수)`로 노출한다                                                         |
| 에이전트가 애매한 항목을 체크해 버렸다                                                                                                                                                           | 완료 조건을 검증 가능한 문장으로 쓰고, 충족 못 한 항목은 체크하지 않고 보고한다                 |
| 에이전트가 문서를 읽지 않고 사용자에게 되물었다                                                                                                                                                  | 읽기 순서를 무조건 실행되는 번호 단계로 두고, 마지막에 "묻기 전에 여기까지 확인한다"를 명시한다 |
| 에이전트가 혼자 긴 문서를 길이 기준으로 쪼개 엉뚱한 경계가 생겼다                                                                                                                                | 200줄 초과 시 분리 기준과 예상 줄 수를 제안해 승인을 받는다                                     |

## 수명 기준 분리

보통 문서를 주제나 길이로 나누지만, 이 구조는 **언제 갱신되는지**로 나눈다.

| 수명         | 예                   | 갱신 시점               |
| ------------ | -------------------- | ----------------------- |
| 영구         | 구조 결정            | 구조 결정이 바뀔 때만   |
| 환경 단위    | 기기별 실측값과 예산 | 기기나 모델을 바꿀 때   |
| 개월 단위    | 단계 구분            | 단계가 끝날 때          |
| 시간~일 단위 | 작업 스텝 체크       | 체크 하나를 끝낼 때마다 |

같은 주제라도 수명이 다르면 분리한다. "어떤 모델을 쓰는가"는 구조 결정이지만 "이 GPU에서 측정한 메모리 사용량"은 기기가 바뀌면 전부 무효가 된다. 섞어 두면 측정값을 고칠 때마다 구조 문서를 건드리게 되고 구조 문서의 신뢰도가 떨어진다.

## 진행 추적 3계층

| 계층       | 단위        | 어디에                         | 수명              |
| ---------- | ----------- | ------------------------------ | ----------------- |
| 단계       | 수개월      | `ROADMAP.md`의 Phase 상태 줄   | 영구 보존         |
| 작업       | 수시간~수일 | 작업 폴더의 스텝 파일 체크박스 | 영구 보존         |
| 세션 할 일 | 수분        | 에이전트의 내부 할 일 목록     | 세션 종료 시 소멸 |

세 번째를 파일로 만들지 않는 것이 중요하다. 커밋 노이즈만 늘고 아무도 읽지 않는다.

## 지침 문서와 실행 제약의 차이

문서는 에이전트에게 하라고 **말할 뿐**이고, 읽지 않거나 다르게 해석할 수 있다. 실제로 막아야 하는 것은 실행 경로를 제거해야 한다.

- 문서로 충분: 분리 기준, 작성 형식, 읽기 순서, 완료 조건 작성법
- 설정이 필요: 승인 없는 커밋·푸시 차단, 되돌릴 수 없는 명령 차단 (에이전트 설정 파일의 권한 거부 목록)

## 일반화 범위

### 어느 프로젝트에나 적용한다

`docs/tasks/` + `docs/structure/` 2분할, 진입점 하나에서 진행 상태를 먼저 읽는 경로, 수명 기준 분리, 3계층 진행 추적과 4곳 동기화, 체크박스 입도 규칙, 작업 시작 절차, 200줄 분리 승인, 역참조 필수, 검증 가능한 완료 조건.

### 프로젝트 전용이므로 이 스킬에 넣지 않는다

- `RUNTIME.md`, `SECURITY.md` 같은 구체적 파일명. 전자는 로컬 하드웨어 제약이 큰 프로젝트에서만, 후자는 권한 경계가 제품 핵심일 때만 의미가 있다. "수명이 다른 축이 있으면 분리한다"는 원리로만 적용한다.
- Phase 개수와 각 단계의 기간
- 작업 번호와 그 범위
- 문서 작성 언어와 문체
