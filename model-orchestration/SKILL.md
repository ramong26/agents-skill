# 모델 오케스트레이션

상위 세션이 사용자의 목표와 아키텍처를 책임진다. 독립 작업만 모델 지정이 가능한 하위 에이전트 또는 별도 Codex 작업에 위임하고, 결과를 직접 통합·검증한 뒤 완료 여부를 결정한다. 모델 선택은 매 요청에서 받으며 특정 모델군이나 모델 전용 스킬을 고정하지 않는다.

## 모델 선택 입력

자연어 또는 다음 형식으로 상위·하위 모델을 받는다.

```text
상위 모델: <정식 모델 ID>
상위 추론 강도: <강도> (선택)
하위 모델: <정식 모델 ID> (위임 경로에서 필요)
하위 추론 강도: <강도> (선택)
검토 모델: <정식 모델 ID> (선택)
검토 추론 강도: <강도> (선택)
모드: solo | delegate | audit | full (선택)
병렬 작업자 수: 자동 | <숫자> (선택)
```

예시:

```text
상위 모델: gpt-6-astra
상위 추론 강도: high
하위 모델: gpt-6-luna
하위 추론 강도: max
병렬 작업자 수: 자동
```

예시의 모델 ID는 현재 런타임에서 지원되는지 실행 전에 확인한다. 예시를 고정된 허용 목록으로 취급하지 않는다.

- 모델 ID와 추론 강도는 별도 값이며 이번 요청에만 적용한다. `6-high`처럼 둘을 합친 별칭은 현재 런타임에서 정확히 하나의 모델과 강도 조합으로 확인될 때만 해석한다. 새 모델은 스킬에 별칭을 추가하지 않고 정식 ID로 선택할 수 있어야 한다.
- 상위 모델은 현재 대화를 실행 중인 모델이며, 채팅 입력만으로 바뀌지 않는다. 사용자는 요청 전에 Codex의 모델 선택기에서 상위 모델을 선택해야 한다. 런타임이 현재 모델을 제공하고 입력과 다르면 위임을 시작하지 않는다. 런타임이 모델 정보를 제공하지 않으면 확인을 강제하지 말고 요청값으로 기록하되, 실행 모델을 확인하지 못했다고 최종 보고에 표시한다.
- `solo` 경로에서는 상위 모델만 필요하다. 하위 모델·검토 모델 입력을 요구하지 않는다. `delegate`와 `full`에서 구현을 위임할 하위 모델이 빠졌으면 위임 전에 묻는다. `audit`은 검토 모델 또는 하위 모델 중 하나가 있으면 실행할 수 있다.
- 먼저 사용 가능한 위임 도구가 모델 ID와 추론 강도 입력을 지원하는지 확인하고, 지원하면 해당 필드로 전달한다.
- 직접 위임 도구가 모델을 지정할 수 없으면 `mcp__codex_app__create_thread`가 사용 가능할 때 별도 Codex 작업을 만들고 `model`과 `thinking`으로 하위 모델을 지정한다.
- 현재 프로젝트 ID가 없으면 `mcp__codex_app__list_projects`에서 작업 저장소와 일치하는 프로젝트를 찾는다. 코드 저장소는 격리된 worktree에서 실행하고, 기존 미커밋 변경이 하위 작업에 필요하면 `startingState: working-tree`를 지정한다. 브랜치나 ref를 임의로 만들지 않는다.
- 작업 생성 뒤 `mcp__codex_app__wait_threads`로 완료를 기다리고 `mcp__codex_app__read_thread`로 결과를 읽는다. 설정 중이라 `clientThreadId`만 반환되면 `mcp__codex_app__list_threads`에서 실제 `threadId`가 준비된 것을 확인한 뒤 thread 전용 도구를 호출한다.
- 모델 지정이 가능한 위임 도구와 별도 Codex 작업 생성 도구를 모두 사용할 수 없거나 지정값으로 실행을 시작하지 못하면, 같은 모델의 하위 에이전트로 조용히 대체하지 말고 한계를 보고한다.
- 위임 도구가 실행된 모델 ID를 반환하지 않을 수 있다. 모델 확인을 위해 지원되지 않는 런타임 조회를 요구하지 않는다. 최종 보고에서는 요청한 모델, 도구에 지정한 모델, 런타임에서 확인된 모델을 구분하고 확인 정보가 없으면 `실행 모델 확인 불가`로 표시한다.
- `delegate`와 `full`에서 구현 작업을 하위에 맡기려면 하위 모델이 필요하다. `audit`은 검토 모델이 지정됐으면 그 모델을 사용하며, 리뷰만 요청한 경우 구현용 하위 모델을 요구하지 않는다. 리뷰 모델이 없고 대체할 하위 모델도 없으면 위임 전에 검토 모델을 한 번에 물어본다. 추론 강도를 생략하면 도구 기본값을 사용하고 확인 가능한 값만 보고한다. 선택값을 다음 작업으로 이월하지 않는다.

## 실행 경로

요청한 최종 상태와 저장소 흐름을 먼저 파악하고, 무엇이 독립적으로 진행될 수 있는지 정한다. 요구사항 결정, 아키텍처와 인터페이스, 작업 분해, 결과 통합, 최종 승인은 상위 세션이 맡는다.

첫 위임 전에 다음 경로를 선언한다.

```text
MODEL ROUTE
mode: solo | delegate | audit | full
risk: <작업별 판단 근거>
primary: <요청한 상위 모델>/<추론 강도 또는 기본값>
worker/reviewer: <도구에 지정한 모델>/<추론 강도 또는 없음>
parallel work: <독립 작업 목록 또는 없음>
```

- `solo`: 기본 경로다. 작고 한 덩어리인 작업이거나 독립적으로 나눌 부분이 없으면 상위 세션에서 처리한다. 병렬화를 위해 가짜 작업을 만들지 않는다.
- `delegate`: 서로 독립된 구현 조각이 둘 이상일 때 사용한다. 모델 지정 필드를 지원하는 하위 에이전트 또는 별도 Codex 작업에 나누고 상위 세션이 통합·검증한다. 별도 리뷰어는 추가하지 않는다.
- `audit`: 사용자가 리뷰만 요청했거나, 구현 결과에 별도의 독립 리뷰가 필요할 때 사용한다. 리뷰만 요청한 경우 상위 세션과 리뷰어 모두 읽기 전용으로 조사하고 어떤 파일도 수정하지 않는다. 검토 모델을 우선 사용하고, 지정되지 않았다면 하위 모델을 리뷰어로 쓴다. 리뷰 전용 요청에는 구현용 작업자가 필요 없다. 구현 결과에 대한 독립 리뷰라면 상위 세션은 구현·검증할 수 있지만 리뷰어는 새 컨텍스트에서 읽기 전용으로 검토하고 수정하지 않는다.
- `full`: 사용자가 기획부터 완료까지 전체 흐름을 요청했거나, 여러 독립 구현 작업과 함께 통합 위험이 큰 경우에 사용한다. 인증·권한·보안, 결제·개인정보, 데이터 마이그레이션·손실, 되돌리기 어려운 배포가 위험 신호다. 상위 세션이 목표와 완료 조건을 정하고, 모델 지정이 가능한 하위 에이전트 또는 별도 Codex 작업에 구현을 위임하고, 결과를 통합·검증한 뒤 새 컨텍스트의 리뷰어에게 읽기 전용 검토를 맡긴다. 독립 구현은 필요 없고 리뷰만 필요한 경우에는 `audit`을 사용한다.
- 별도 검토 모델이 지정되면 그 모델을 사용한다. 지정되지 않았다면 하위 모델을 검토에도 사용할 수 있다. 리뷰 전용 `audit`에 두 모델 모두 없으면 검토 모델을 요청한다.
- `delegate` 경로는 서로 독립된 작업만 동시에 실행한다. 작업 개수에 맞는 최소 인원만 사용한다. 같은 파일을 여러 에이전트에 동시에 맡기지 말고, 겹치는 작업은 소유 범위를 분리하거나 순서대로 실행한다.
- 각 하위 작업에는 아래 계약을 전달한다. 구현 작업은 가능한 한 정확한 파일 소유 범위를 지정하고, 조사·리뷰 작업은 읽기 전용 범위를 적는다.

```text
목표: 무엇을 끝낼지
담당 범위: 수정할 파일·영역 또는 읽기 전용 조사 범위
관련 맥락/인터페이스: 필요한 배경과 지켜야 할 연결 규약
하지 않을 것: 범위 밖 수정이나 결정
완료 조건: 끝났다고 판단할 기준
검증: 수행할 확인 또는 실행할 명령
완료 보고: 상태 / 변경 파일 / 변경 요약 / 검증 결과 / 결정·가정 / 미완료·위험
```

- 하위 작업의 완료 보고에서 `완료`, `부분 완료`, `막힘`을 구분하게 한다. 검증을 실행하지 않았으면 통과한 것처럼 보고하지 않도록 한다.

## 상위 세션의 통합과 승인

- 하위 에이전트의 보고는 주장으로 취급한다. 상위 세션이 실제 결과와 변경 범위를 확인하고, 서로 충돌하는 결과를 조정한다.
- 코드 작업에서는 누적 diff를 직접 검토하고 변경에 맞는 검증을 수행한다. 하위 에이전트의 통과 보고만으로 완료 처리하지 않는다.
- `audit`과 `full`의 리뷰어는 통합된 변경을 독립적으로 읽고, 발견 사항과 근거를 보고한다. 리뷰어는 코드를 수정하지 않는다. 리뷰 결과는 다음 판정 형식을 사용한다.

```text
판정: 통과 | 수정 필요 | 검토 불가
발견 사항: 우선순위(차단 | 비차단) / 파일과 위치 / 영향 / 근거 / 권장 수정
검토 범위와 미확인 사항:
```

- `통과`는 완료를 막는 미해결 문제가 없다는 뜻이며 비차단 개선점은 함께 남길 수 있다. `수정 필요`는 차단 발견 사항이 있다는 뜻이고, `검토 불가`는 정보나 도구가 부족해 판단할 수 없다는 뜻이다. 발견 사항마다 우선순위와 근거를 적는다.
- 별도 Codex 작업이 격리된 worktree를 사용하면 변경이 상위 작업 디렉터리에 자동 반영된다고 가정하지 않는다. 하위 작업에서 diff·패치 또는 커밋을 받아 상위 세션이 검토하고 현재 작업에 통합한 뒤 전체 변경을 검증한다. 결과를 가져올 수 없으면 완료로 보고하지 않는다.
- 리뷰에서 수정이 필요하면 상위 세션이 직접 수정하거나 해당 하위 작업만 명확히 다시 위임한다. 수정 후 상위 세션이 다시 검증하고, 새 컨텍스트의 리뷰어가 수정된 부분과 관련 경로를 재검토한다. 이전 리뷰 승인을 새 변경에 재사용하지 않는다.
- 모델 지정이 가능한 위임 도구와 별도 Codex 작업 생성 도구를 모두 사용할 수 없으면 요청된 하위 모델 병렬 실행이 불가능하다고 알린다. 여러 역할 프롬프트를 작성한 것을 실제 하위 모델 실행으로 표현하지 않는다.
- 최종 보고에는 요청한 모델과 추론 강도, 도구에 지정한 모델, 런타임 확인 여부, 병렬 작업, 상위 세션의 검증 근거, 미완료 항목을 구분해 적는다.
