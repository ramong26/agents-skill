# 모델 오케스트레이션

상위 세션이 사용자의 목표와 아키텍처를 책임진다. 현재 Codex 세션을 상위 모델로 사용하고, 독립 작업만 하위 에이전트 또는 별도 Codex 작업에 위임한다. 사용자가 하위·검토 모델을 지정하면 그 값을 우선하고, 지정하지 않으면 TypeSafe Jev가 실제 실행 가능한 후보 중에서 선택한다. 결과는 상위 세션이 직접 통합·검증한다.

## 모델 선택 입력

사용자가 필요하면 자연어 또는 다음 형식으로 하위 모델과 작업 경로를 지정할 수 있다. 상위 모델 입력은 받지 않는다.

```text
하위 모델: <정식 모델 ID> (선택; 없으면 Jev가 선택)
하위 추론 강도: <강도> (선택)
검토 모델: <정식 모델 ID> (선택)
검토 추론 강도: <강도> (선택)
모드: solo | delegate | audit | full (선택)
병렬 작업자 수: 자동 | <숫자> (선택)
```

예시:

```text
하위 모델: gpt-6-luna
하위 추론 강도: max
병렬 작업자 수: 자동
```

예시의 모델 ID는 현재 런타임에서 지원되는지 실행 전에 확인한다. 예시를 고정된 허용 목록으로 취급하지 않는다.

- 모델 ID와 추론 강도는 별도 값이며 이번 요청에만 적용한다. `6-high`처럼 둘을 합친 별칭은 현재 런타임에서 정확히 하나의 모델과 강도 조합으로 확인될 때만 해석한다. 새 모델을 스킬의 고정 허용 목록으로 만들지 않는다.
- 현재 대화 세션이 상위 모델이다. 상위 모델을 입력받거나 바꾸려 하지 않는다. 런타임이 세션 모델 ID를 제공하지 않으면 확인을 강제하지 말고 최종 보고에 `세션 모델 ID 확인 불가`로 표시한다.
- `solo` 경로에서는 하위 모델이나 Jev 호출이 필요 없다. 위임이 필요한데 하위 모델이 지정되지 않았으면 아래 Jev 선택 절차를 따른다. 사용자가 모델을 지정하지 않았다는 이유만으로 먼저 되묻지 않는다.
- 위임 전에 도구와 모델 지정 입력을 확인한다. 네이티브 하위 에이전트의 `model` override를 우선하고, 없으면 `mcp__codex_app__create_thread`의 `model` override를 사용한다. 실제 모델을 지정할 경로가 없으면 기본 모델로 몰래 위임하지 않는다.
- 필요한 하위 모델이 지정되지 않았으면 선택한 위임 경로의 실제 `model` 입력이 지원하는 모델만 후보로 만든다. 복수 후보는 [JEV 모델 라우팅](references/jev-router.md)의 공식 `typesafe-sdk` 호출과 `Choice`로 고르고, 현재 후보에 대한 응답의 선택값을 검증한다. TypeSafe SDK/API 연결이나 인증이 없으면 자동 선택을 주장하지 말고, 빠진 설정을 보고한다. 의존성을 자동 설치하거나 API 키를 채팅으로 요청하지 않는다.
- Jev에는 짧고 비식별화한 작업 요약, 작업 유형·위험도, 하위 작업 역할, 후보 ID와 도구 설명만 제공한다. 코드·비밀값·개인정보는 전송하지 않는다. 후보는 정확한 모델 ID여야 하며, 반환값을 일대일로 실제 위임 입력에 연결한다. 같은 요청의 병렬 작업은 한 번 고른 모델을 공유한다. confidence는 작업 위험도와 함께 판단하고 보편적인 고정 임계값이나 정답 보증으로 취급하지 않는다.
- Jev가 고른 정확한 ID를 위임 호출의 실제 `model` override에 전달한다. ID를 작업 프롬프트에 적는 것만으로 모델 지정이 되었다고 보지 않는다. 별도 Codex 작업으로 위임할 때도 `create_thread`의 `model`에 같은 ID를 전달한다. 추론 강도는 사용자가 지정한 경우에만 지원 입력으로 전달하고, 없으면 도구 기본값을 사용한다.
- Jev가 반환한 모델 ID가 후보에 없거나 선택 신뢰도·연결 상태가 작업 위험도에 비해 부족하면 하위 모델을 실행하지 않는다. 기본 모델로 조용히 대체하지 말고 실패 사유와 명시적 모델 지정 또는 재시도 경로를 알린다. 지원 후보가 하나뿐일 때는 API를 호출하지 않고 그 후보를 사용하되 `단일 지원 후보`라고 보고한다.
- 사용자가 검토 모델을 지정하지 않으면 구현용으로 명시되거나 Jev가 고른 하위 모델을 리뷰에도 재사용한다. 리뷰 전용 `audit`에서는 사용자가 하위 모델이나 검토 모델을 지정하지 않은 경우에만 Jev가 리뷰어 모델을 선택한다.
- 위임 뒤 도구가 실제 모델 ID를 반환하면 Jev 또는 사용자가 고른 ID와 일치하는지 확인한다. 다르면 해당 작업을 Jev 선택 모델로 실행했다고 취급하지 말고 추가 위임을 멈춰 불일치를 보고한다. 지원되지 않는 조회를 요구하지 말고, 실제 ID를 확인할 수 없으면 전달한 override 값과 런타임 확인 불가를 구분해 보고한다.
- 현재 프로젝트 ID가 없으면 `mcp__codex_app__list_projects`에서 작업 저장소와 일치하는 프로젝트를 찾는다. 코드 저장소는 격리된 worktree에서 실행하고, 기존 미커밋 변경이 하위 작업에 필요하면 `startingState: working-tree`를 지정한다. 브랜치나 ref를 임의로 만들지 않는다.
- 작업 생성 뒤 `mcp__codex_app__wait_threads`로 완료를 기다리고 `mcp__codex_app__read_thread`로 결과를 읽는다. 설정 중이라 `clientThreadId`만 반환되면 `mcp__codex_app__list_threads`에서 실제 `threadId`가 준비된 것을 확인한 뒤 thread 전용 도구를 호출한다.
- 모델 지정이 가능한 위임 경로를 사용할 수 없거나 지정한 모델로 실행을 시작하지 못하면, 기본 모델·현재 세션 모델로 조용히 대체하지 말고 한계를 보고한다.
- `delegate`와 `full`에서 구현 작업을 위임할 때 하위 모델이 지정되지 않았으면 Jev가 선택한다. `audit`은 검토 모델, 하위 모델 순으로 사용자가 지정한 값을 우선하고, 둘 다 없으면 Jev가 리뷰어 모델을 고른다. 추론 강도를 생략하면 도구 기본값을 사용하고 확인 가능한 값만 보고한다. 사용자 지정과 Jev 판단을 다음 작업으로 이월하지 않는다.

## 실행 경로

요청한 최종 상태와 저장소 흐름을 먼저 파악하고, 무엇이 독립적으로 진행될 수 있는지 정한다. 요구사항 결정, 아키텍처와 인터페이스, 작업 분해, 결과 통합, 최종 승인은 상위 세션이 맡는다.

첫 위임 전에 다음 경로를 선언한다.

```text
MODEL ROUTE
mode: solo | delegate | audit | full
risk: <작업별 판단 근거>
primary: <현재 세션>/<런타임 ID 또는 확인 불가>
worker/reviewer: <사용자 지정 또는 Jev 선택 모델>/<추론 강도 또는 도구 기본값>/<선택 출처·confidence>
model override: <위임 도구>.model=<선택된 정확한 ID> | 미실행
parallel work: <독립 작업 목록 또는 없음>
```

- `solo`: 기본 경로다. 작고 한 덩어리인 작업이거나 독립적으로 나눌 부분이 없으면 상위 세션에서 처리한다. 병렬화를 위해 가짜 작업을 만들지 않는다.
- `delegate`: 서로 독립된 구현 조각이 둘 이상일 때 사용한다. 사용자 지정 모델을 우선하고, 없으면 Jev가 실제 위임 도구에서 선택 가능한 모델 중 하나를 고른다. 상위 세션이 통합·검증하고 별도 리뷰어는 추가하지 않는다.
- `audit`: 사용자가 리뷰만 요청했거나, 구현 결과에 별도의 독립 리뷰가 필요할 때 사용한다. 리뷰만 요청한 경우 상위 세션과 리뷰어 모두 읽기 전용으로 조사하고 어떤 파일도 수정하지 않는다. 검토 모델, 하위 모델 순으로 사용자가 지정한 값을 우선하고 둘 다 없으면 Jev가 리뷰어 모델을 고른다. 리뷰 전용 요청에는 구현용 작업자가 필요 없다. 구현 결과에 대한 독립 리뷰라면 상위 세션은 구현·검증할 수 있지만 리뷰어는 새 컨텍스트에서 읽기 전용으로 검토하고 수정하지 않는다.
- `full`: 사용자가 기획부터 완료까지 전체 흐름을 요청했거나, 여러 독립 구현 작업과 함께 통합 위험이 큰 경우에 사용한다. 인증·권한·보안, 결제·개인정보, 데이터 마이그레이션·손실, 되돌리기 어려운 배포가 위험 신호다. 상위 세션이 목표와 완료 조건을 정하고, 사용자 지정 모델 또는 Jev가 고른 모델로 구현을 위임하고, 결과를 통합·검증한 뒤 새 컨텍스트의 리뷰어에게 읽기 전용 검토를 맡긴다. 독립 구현은 필요 없고 리뷰만 필요한 경우에는 `audit`을 사용한다.
- 별도 검토 모델이 지정되면 그 모델을 사용한다. 지정되지 않았다면 선택된 구현용 하위 모델을 검토에도 재사용한다. 리뷰 전용 `audit`에는 Jev가 고른 리뷰어 모델을 사용한다.
- `delegate` 경로는 서로 독립된 작업만 동시에 실행한다. 작업 개수에 맞는 최소 인원만 사용한다. 같은 파일을 여러 에이전트에 동시에 맡기지 말고, 겹치는 작업은 소유 범위를 분리하거나 순서대로 실행한다.
- 각 하위 작업에는 아래 계약을 전달한다. 구현 작업은 가능한 한 정확한 파일 소유 범위를 지정하고, 조사·리뷰 작업은 읽기 전용 범위를 적는다.

```text
목표: 무엇을 끝낼지
담당 범위: 수정할 파일·영역 또는 읽기 전용 조사 범위
관련 맥락/인터페이스: 필요한 배경과 지켜야 할 연결 규약
하지 않을 것: 범위 밖 수정이나 결정
완료 조건: 끝났다고 판단할 기준
검증: 수행할 확인 또는 실행할 명령
완료 보고: 상태 / 변경 파일 / 변경 요약 / 검증 결과 / 결정·가정 / 미완료·위험
```

- 하위 작업의 완료 보고에서 `완료`, `부분 완료`, `막힘`을 구분하게 한다. 검증을 실행하지 않았으면 통과한 것처럼 보고하지 않도록 한다.

## 상위 세션의 통합과 승인

- 하위 에이전트의 보고는 주장으로 취급한다. 상위 세션이 실제 결과와 변경 범위를 확인하고, 서로 충돌하는 결과를 조정한다.
- 코드 작업에서는 누적 diff를 직접 검토하고 변경에 맞는 검증을 수행한다. 하위 에이전트의 통과 보고만으로 완료 처리하지 않는다.
- `audit`과 `full`의 리뷰어는 통합된 변경을 독립적으로 읽고, 발견 사항과 근거를 보고한다. 리뷰어는 코드를 수정하지 않는다. 리뷰 결과는 다음 판정 형식을 사용한다.

```text
판정: 통과 | 수정 필요 | 검토 불가
발견 사항: 우선순위(차단 | 비차단) / 파일과 위치 / 영향 / 근거 / 권장 수정
검토 범위와 미확인 사항:
```

- `통과`는 완료를 막는 미해결 문제가 없다는 뜻이며 비차단 개선점은 함께 남길 수 있다. `수정 필요`는 차단 발견 사항이 있다는 뜻이고, `검토 불가`는 정보나 도구가 부족해 판단할 수 없다는 뜻이다. 발견 사항마다 우선순위와 근거를 적는다.
- 별도 Codex 작업이 격리된 worktree를 사용하면 변경이 상위 작업 디렉터리에 자동 반영된다고 가정하지 않는다. 하위 작업에서 diff·패치 또는 커밋을 받아 상위 세션이 검토하고 현재 작업에 통합한 뒤 전체 변경을 검증한다. 결과를 가져올 수 없으면 완료로 보고하지 않는다.
- 리뷰에서 수정이 필요하면 상위 세션이 직접 수정하거나 해당 하위 작업만 명확히 다시 위임한다. 수정 후 상위 세션이 다시 검증하고, 새 컨텍스트의 리뷰어가 수정된 부분과 관련 경로를 재검토한다. 이전 리뷰 승인을 새 변경에 재사용하지 않는다.
- 최종 보고에는 현재 세션 모델 ID의 확인 여부, 사용자 지정 또는 Jev가 실제로 선택한 하위 모델과 추론 강도, 도구에 지정한 값, 선택 출처와 확인된 confidence, 병렬 작업, 상위 세션의 검증 근거, 미완료 항목을 구분해 적는다. solo라 Jev를 호출하지 않았거나 단일 지원 후보였거나 연결 문제로 호출하지 못한 경우도 명시한다.
